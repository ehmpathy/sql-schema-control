# vision: fix bin/run broken reference

## the outcome world

### day-in-the-life

a developer installs sql-schema-control via `npm install sql-schema-control` and runs `npx sql-schema-control plan`. it works. no cryptic "Cannot find module '../src/contract/cli'" errors.

### before/after contrast

| before | after |
|--------|-------|
| `npx sql-schema-control plan` → `Cannot find module '../src/contract/cli'` | `npx sql-schema-control plan` → shows execution plan |
| published package broken, unusable | published package works as advertised |
| no acceptance test catches this | acceptance test verifies cli works after pack |

### aha moment

"wait, the package was shipping a bin that required code we never included in the publish. of course it broke."

## user experience

### usecases

1. **install and run cli**: `npm install sql-schema-control && npx sql-schema-control plan`
2. **run acceptance tests locally**: `npm run test:acceptance:locally` catches the bin/run bug before publish

### contract inputs & outputs

**bin/run** (entrypoint):
- input: none (cli args parsed by commander)
- output: runs cli commands (plan, apply, sync, pull)

**acceptance tests** (3 total, all via subprocess against bin/run):

1. **--help**: verifies bin/run can load and show help
   - input: `./bin/run --help`
   - output: help text, exit 0

2. **plan with .js config**: verifies bin/run works with javascript config
   - input: genTempDir with `control.yml` + `connection.config.js`
   - command: `./bin/run plan -c {tempDir}/control.yml`
   - output: plan output, exit 0

3. **plan with .ts config**: verifies tsx registration works for typescript configs
   - input: genTempDir with `control.yml` + `connection.config.ts`
   - command: `./bin/run plan -c {tempDir}/control.yml`
   - output: plan output, exit 0

### timelines

1. developer makes changes
2. runs `npm run test` (includes acceptance test)
3. acceptance test fails if bin/run references missing paths
4. developer fixes bin/run before publish

## mental model

### how users describe this

"the cli wasn't working when installed from npm. bin/run was looking for source files that aren't published."

### analogies

like shipping a car with the ignition pointing to a missing engine. the key goes in, but the car doesn't start.

### terms

| user term | our term |
|-----------|----------|
| "broken install" | bin/run references unpublished src/ |
| "cli doesn't work" | require('../src/contract/cli') fails |

## evaluation

### how well does it solve the goals?

| goal | solution |
|------|----------|
| reproduce defect | acceptance test runs cli via subprocess after build |
| prevent regression | test runs on every PR via CI |
| fix the bug | change bin/run to require dist instead of src |

### pros

- simple fix: one line change in bin/run (just the require path)
- acceptance test catches this class of bugs permanently
- no breaking changes to users
- preserves .ts config file support

### cons

- requires `npm run build` before cli works in dev (already true)

### edgecases

| edge | mitigation |
|------|------------|
| dev runs bin/run without build | fails with clear error (expected — must build first) |
| dist not in publish | already listed in package.json files array |

## open questions & assumptions

### assumptions

1. `dist/contract/cli.js` will exist after build (verified: build compiles to dist/)
2. ~~tsx runtime not needed at runtime when requiring compiled js~~ **WRONG** — tsx IS needed at runtime to support .ts config files (see `getConnectionConfig.ts` line 13: `require(modulePath)` where modulePath can be `.ts`)

### questions for wisher

none — the fix is straightforward.

### external research needed

## groundwork

### external research

none — no external apis or services referenced.

### internal research

**bin/run (line 5)**:
```js
const { run } = require('../src/contract/cli');
```
references `src/` which is NOT in the published files.

**package.json files array (line 27-31)**:
```json
"files": [
  "/bin",
  "/dist",
  "/schema"
]
```
only `/bin`, `/dist`, `/schema` are published. `/src` is not.

**src/contract/cli.ts**:
exports `run()` function that creates commander program and parses args.

**fix**:
1. keep `require('tsx/cjs')` — needed for .ts config file support
2. change path from `../src/contract/cli` to `../dist/contract/cli`
3. keep tsx in dependencies — IS a runtime requirement for .ts config files

result bin/run:
```js
#!/usr/bin/env node
require('tsx/cjs');
const { run } = require('../dist/contract/cli');
run().catch((error) => {
  console.error(error);
  process.exit(1);
});
```

**note**: tsx stays in dependencies because users can have `.ts` config files that get loaded via `require(modulePath)` at runtime.

## what is awkward?

### the test approach

running the cli via subprocess in an acceptance test is slightly indirect. but it's the only way to truly verify what users experience — the published bin/run executable working end-to-end.

### dev mode story

after this fix, running `./bin/run` directly in development requires `npm run build` first. but this is already the expected workflow. the dist reference is more honest about what gets published.

tsx remains registered so users with `.ts` config files still work.
